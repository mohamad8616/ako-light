**Timezone gotcha (bit me hard)**
- `verification.expiresAt`/`createdAt` are Postgres `timestamp` (NO time zone). Prisma
  writes local wall-clock; node-pg parses it back in local zone (this machine: Iran,
  UTC+3:30). So `expiresAt` read via raw pg is **3.5h off** from `Date.now()` and
  `expiresAt > Date.now()` is ALWAYS false. Fix: compare the row's two columns to each
  other (`otpTtlSeconds` → exactly 300), never to `Date.now()`. `expireStoredOtp` uses
  `createdAt - 1s`, not `now()`.

**Discovered behaviours (verified in better-auth source, not assumed)**
- `/sign-up/email` **also creates a session** — every test user starts with one
  `session` row. `registerUser` now returns `signUpSession: { jar }` so this is
  explicit; session-count assertions account for it.
- `/sign-in/email` returns `token: session.token` = the **raw DB token** (the
  cookie is a separate HMAC wrapper). Asserted equality to the stored row.
- Ban enforcement lives ONLY in the admin plugin's `session.create` hook —
  `/get-session` has no ban check. So an existing pre-ban session row remains
  but cannot mint a new one.

**BUG FIXED — multi-file crash: Next dev lockfile → `process.exit(1)`**
Running the whole `auth` tier (≥2 files) killed the worker: `phone-otp`'s
send-otp 500'd and all later tests showed as skipped. Root cause
(`next/dist/build/lockfile.js:166-210`): Next takes an exclusive lock at
`<distDir>/lock` with `unlockOnExit`, and if it cannot acquire it within
`MAX_RETRY_MS = 1000` it calls `process.exit(1)`. With `fileParallelism:false`
every file runs in ONE forked worker, so file N+1 booted inside the window
where file N's native unlock (triggered by `app.close()`) had not landed yet.
**Fix:** `serverTeardown` barrier in `tests/helpers/auth-db.ts` — `close()` sets
a 1500ms settle promise, `startAuthServer()` awaits it before booting, and
`stopAuthServer()` awaits it too. Auth tier now 5 files / 55 tests / 0 fail.

**FINDING (reported, NOT fixed — out of scope): timezone skew on `banExpires`**
`user.banExpires` is `TIMESTAMP(3)` (no time zone; see migration
`20260915115639_add_phone_otp_support`). The plugin compares
`new Date(banExpires).getTime() < Date.now()`. Prisma reads a bare `timestamp`
as **UTC**, but this machine is UTC+3:30, so a `banExpires` written as
"now − 60s" round-trips ~3.5h into the FUTURE and reads as a live ban — i.e. an
expired temporary ban would NOT auto-lift for a user in a non-UTC zone. Proved
with a Prisma probe: `SELECT '2026-09-28 20:59:13'::timestamp` → `20:59:13Z`
while `now()` → `17:32Z`. The banned tests use a ±12h offset so they pin the
mechanism independent of the skew. A proper fix would migrate the column to
`timestamptz` — deliberately not done here (schema change beyond this pass).
