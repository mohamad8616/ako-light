# 2026-09-30

## Order confirmation notifications (SMS + email after a successful payment)

Fired from the ZarinPal verification success path in
`app/[locale]/(site)/checkout/callback/page.tsx`, on the `pending → paid`
transition only (guarded by the pre-update status, so refreshing the callback or
reopening the link from the receipt does NOT re-send).

**Channel policy — SMS first, email as fallback.** Decided with the user.
The two contact sources are NOT equally reliable:

- `User.phoneNumber` — set/verified only for phone-based accounts.
- `Order.phone` — always present (checkout requires it) but unverified.
- `User.email` — ALWAYS present, but phone sign-ups get a synthetic
  `<phone>@phone.ako-light.local` address that cannot receive mail.

**`emailVerified` is NOT a usable filter** — this project doesn't require email
verification, so email/password sign-ups leave it `false` and a real, working
address would be discarded. The synthetic DOMAIN is the reliable discriminator.

**New files**
- `lib/sms/normalize-mobile.ts` — shared Iranian mobile normaliser (extracted
  from `lib/auth/sms.ts` so OTP and receipts cannot drift).
- `lib/notifications/sms.ts` — sms.ir BULK sender.
- `lib/notifications/email.ts` — nodemailer/SMTP sender.
- `lib/notifications/order-receipt-text.ts` — pure policy + formatting.
- `lib/notifications/order-receipt.ts` — IO orchestrator; `sendOrderReceipt`
  NEVER throws (a lost receipt must not break the confirmation page).

**Email provider: nodemailer + generic SMTP.** The user's rule was "free
first". nodemailer is free and provider-agnostic (works with a free Gmail
app-password or an Iranian host); Resend/SendGrid are free-*tier* only and
their API hosts are often unreachable from Iran.

### sms.ir BULK endpoint (research, confirmed from their docs)

- `POST https://api.sms.ir/v1/send/bulk`, header `X-API-KEY`.
- Body: `{ lineNumber, messageText, mobiles: string[] }` (max 100 mobiles).
- Response: `{ status: 1, message: "موفق", data: { packId, messageIds, cost } }`.
- **`lineNumber` is mandatory** — a dedicated sending line. The Verify endpoint
  does NOT need one, hence the new `SMSIR_LINE_NUMBER`.
- **Sandbox for bulk is NOT documented.** sms.ir publishes a concrete sandbox
  example only for `/send/verify` (fixed template `123456`). Their generic claim
  is that the sandbox mirrors production shape, but there is no bulk sandbox
  example. So bulk + sandbox key is UNCONFIRMED — never assume it.

### BUG FIXED: country code was never stripped

`normalizeMobile` in `lib/auth/sms.ts` claimed in its docstring to accept
`+98919xxxx904`, but the implementation only dropped a leading `0` from an
11-digit number — `+98…` became **12 digits** and sms.ir would reject it.
better-auth stores phone-account numbers in E.164 form, so this was the COMMON
case, not an edge case, and it would have silently broken every receipt to a
phone-based customer. Fixed in `lib/sms/normalize-mobile.ts` (handles `98…`
length-gated to 12 digits, and `0098…`). Caught by a unit test asserting the
docstring's own promise.

### Test-infra lessons

1. **Two fetch guards must COMPOSE.** `auth-sms-guard.ts` and the new
   `zarinpal-guard.ts` are both setupFiles and both stub `globalThis.fetch`.
   Capturing `globalThis.fetch` at MODULE-EVAL time makes the last-installed
   guard win and silently disables the other (i.e. real SMS could egress).
   Both now capture it inside `beforeAll` and delegate, so they chain.
2. **A stale `.next/dev` makes the in-process dev server 404 routes that exist.**
   `/en/checkout/callback` returned 404 in the auth tier while `/en/checkout`
   and `/en/about` worked, and the route IS in
   `.next/app-path-routes-manifest.json`. `next start` on the production build
   served it 200. Moving `.next/dev` aside fixed it. `rm -rf` was blocked by the
   bulk-delete guard — use `mv` to set it aside.
3. **`next({dev:true})` 404s the first request to a cold route** while it
   compiles. Warm it in `beforeAll` (the new test polls `/api/auth/ok`).
4. **Raw INSERTs must supply `updatedAt`** — Prisma's `@updatedAt` fills it in
   the ORM, so the column has no DB default.
5. The order-receipt e2e test must SET `SMSIR_API_KEY` + `SMSIR_LINE_NUMBER`
   after the server boots. Without the line number the sender correctly takes
   its dev fallback and logs instead of sending, so the test would prove nothing.
6. **The dev server 404s a route while it compiles, and returns FAST** (≈230ms),
   so a retry loop has to outlast the whole compile. A first compile of
   `/en/checkout/callback` was measured at **62s**, of `/en/admin/admins` at
   **72s**. `fetchPageWhenWarm` in tests/helpers/auth-db.ts retries 404 for ~3
   minutes. A 20s budget is not enough and looks exactly like a missing route.
7. **`pnpm run build` needs the sandbox disabled in this environment.** The
   sandbox denies writes to `.next/server/app/[locale]/(admin)/...` (paths with
   brackets/parens) and to `.next/dev/cache/turbopack/*.blob`. When the
   Turbopack cache write is denied the dev server serves 404 and then **500**
   for page routes — which looks like an app bug and is not one. Escalate with
   `dangerouslyDisableSandbox` for the build.

## Re-verification (2026-09-30 03:0x) — supersedes the section above

**Root cause of the auth-tier hang is now IDENTIFIED (it was not DNS).** The
full suite stalls in the `auth` tier because of **port contention on the single
fixed port**, not name resolution:

- `resolveAuthOrigin()` derives the port from `BETTER_AUTH_URL`, and it MUST be
  that exact origin — better-auth validates the `Origin` header against
  `trustedOrigins`, so a random port would turn every mutating call into
  `403 INVALID_ORIGIN`. So every test file binds the SAME port.
- `startAuthServer()`'s `close()` did `httpServer.close()` then `app.close()`.
  `httpServer.close()` does not return until idle keep-alive sockets drain, and
  undici holds them — so the port stayed bound past the 1500ms barrier and the
  NEXT file's `listen()` failed with **EADDRINUSE**, killing the worker and
  reporting the file's tests as *skipped* (which is why a run could exit 1 while
  the reporter still printed `FAIL (0)`).

**Fix (tests/helpers/auth-db.ts):**
1. `close()` now calls `httpServer.closeAllConnections?.()` alongside
   `close()`, so the port is released promptly rather than after a lag.
2. `startAuthServer()` translates a bind failure into an actionable message
   (name the port, explain the stale-dev-server cause) instead of an opaque
   `beforeAll` crash.
3. New `clearStaleDevLock()`: Next only checks that `.next/dev/lock` EXISTS, not
   that its recorded PID is alive, so a lock left by a killed run poisons every
   later run with `process.exit(1)`. The helper probes with
   `process.kill(pid, 0)` and removes the lock ONLY on `ESRCH`; alive or `EPERM`
   leaves it alone.

## SECOND root cause found — corrupted `.next/dev`, not a port race

After fixing the teardown, the tier STILL failed, and the real error surfaced:

```
PageNotFoundError: Cannot find module for page: /api/auth/[...all]/route
  at getPagePath (next/dist/server/require.js:94)
  at async Object.loadStaticPaths (next/dist/server/dev/static-paths-worker.js:41)
```

The route directories EXIST but are EMPTY:

```
.next/dev/server/app/api/auth/[...all]/    # 0 bytes, no files
```

Both manifests (`app-path-routes-manifest.json`, `.next/dev/server/app-paths-manifest.json`)
DO list the route. So the manifest is correct and the **compiled artifact is
missing** — exactly the Turbopack cache-write denial recorded above. In dev,
Next turns the resulting 500 into `process.exit(1)`, which kills the vitest
worker and reports the file's tests as *skipped*.

**This is the failure that produces `PASS (n) FAIL (0)` with exit 1** — the
reporter never counts the tests that never ran. Never trust the reporter's
`FAIL (0)` without checking the test count against the expected total.

**Recovery:** `mv .next/dev .next/dev-stale-<ts>` (it will fail with "Permission
denied" while a dev server still holds handles — wait for port 3000 to go free,
then retry; it succeeds within ~30s). Do NOT `rm -rf` (blocked). Then run and
the cold rebuild repopulates the route artifacts.

**Diagnostic that distinguishes the two causes:**
- `EADDRINUSE` on `listen` → port still bound by a previous file's server.
- `Cannot find module for page: /api/auth/[...all]/route` → stale/empty
  `.next/dev` route artifact (rebuild needed).
- `process.exit unexpectedly called with "1"` at
  `next/build/lockfile.js` → another dev server holds `.next/dev/lock`
  (Next only retries `MAX_RETRY_MS = 1000`, then exits).

**Harness hardening landed (tests/helpers/auth-db.ts):**
- `close()` now calls `httpServer.closeAllConnections?.()` BEFORE awaiting
  `close()` — otherwise `close()` waits on undici's idle keep-alive sockets and
  never resolves, so `app.close()` is never reached and the server outlives the
  run.
- A 5s timeout guards the close promise so teardown can never hang.
- `tornDown` latch: `startAuthServer()` now THROWS if called after
  `stopAuthServer()`. Several helpers (`hitCallback`, `getPage`) call it lazily,
  so a call landing after teardown silently booted a second, uncloseable server.
- `clearStaleDevLock()`: removes `.next/dev/lock` only when the recorded PID is
  gone (`process.kill(pid, 0)` → `ESRCH`); alive or `EPERM` leaves it alone, so
  a genuinely running dev server is never disturbed.
- `EADDRINUSE` is translated into an actionable message naming the port and the
  stale-server cause instead of an opaque `beforeAll` crash.

**Sandbox limits (block recovery from inside the agent):** every child-process
spawn (`tasklist`, `taskkill`, `wmic`) returns `EBUSY`; PowerShell returns empty
output. So a leftover listener cannot be identified or killed here — it must be
waited out (it does exit) or killed by the user.

## THIRD root cause — the auth tier leaks a dev server on every file

The single most important finding of this session, and the reason the tier is
flaky run-to-run:

**Each `auth` test file leaks the server it starts.** Evidence, all observed:

- After a run's vitest process exited, port 3000 was STILL `LISTENING` and
  `/api/auth/ok` answered **200** — i.e. a live server survived the run.
- The owning PID changed constantly across checks (15280 → 11352 → 4156 → 9448
  → 1928 → 14480 → 5092). It is NOT one stable daemon: each run/worker leaks its
  own, and they exit a few seconds to a minute apart.
- While a leaked server holds the port, the NEXT file fails in one of two ways,
  both fatal to the worker:
  1. `EADDRINUSE` at `listen` (outbound);
  2. `process.exit(1)` from `next/dist/build/lockfile.js` (inbound), because the
     leak also holds `.next/dev/lock` and Next retries for only
     `MAX_RETRY_MS = 1000ms` before exiting.
- Because the worker dies, vitest reports the file's tests as **skipped**, and
  the AI reporter still prints `FAIL (0)`. **So `PASS (n) FAIL (0)` with exit
  code 1 is the signature of this bug** — always compare `n` to the expected
  total (700 vs 743 in one run = 43 tests never ran).

**Verified with a minimal isolated probe** (`.probe-close.mjs`, since deleted)
that `next({dev:true}).close()` DOES release the port, and that
`closeAllConnections()` + `close()` DOES release the harness listener. So the
teardown primitives are fine; the leak is in **when/whichever** server isn't
reached by `stopAuthServer()`.

**Leading hypothesis (not yet proven):** `startAuthServer()` is called LAZILY
from helpers as well as from `beforeAll` —
`order-receipt.test.ts` has 6 call sites, `phone-otp` and
`user-management-ui` have 2 each (see `hitCallback`, `getPage`). A call that
lands after `afterAll` teardown, or a second boot that overwrites the
module-level `server` reference while the first is still bound, produces a
server that nothing closes. The new `tornDown` latch turns the
call-after-teardown case into a hard error so it can be proven rather than
guessed.

**Harness work is landed but the tier is NOT yet verified green.** Do not claim
it is. The blocker is environmental: an orphan dev server holds port 3000 for
tens of seconds after each run, and the sandbox forbids the process tools needed
to clear it, so back-to-back verification runs cannot get a clean port.




## Architecture review — findings (2026-09-30)

Full report written to `docs/review/code-review-2026-09-30.md`. Highlights,
verified by reading the code (not inferred):

**Critical bug — stock is never decremented.** `lib/actions/checkout.ts` checks
`product.quantity < quantity` inside the transaction but nothing anywhere ever
writes `Product.quantity` after a paid order (`grep -rn "decrement|quantity:"
lib/` returns only read paths). Oversell is guaranteed and the checkout guard
protects nothing. Fix: guarded `updateMany({ where: { quantity: { gte: q } },
data: { quantity: { decrement: q } } })` inside the same transaction.
Corollary: abandoned `pending` orders leak reservations forever (no sweep).

**Bundle bug — whole dictionary ships to the client.**
`lib/i18n/LanguageProvider.tsx` is a client component importing the
`./translations` barrel (1,763 lines / 107,667 bytes; `admin.ts` alone is
43,347 bytes). 37 files import the barrel; `LanguageProvider` wraps the app
from `app/[locale]/layout.tsx`, so all of it is on the public-site critical
path. Nothing has been changed — this is the finding, not the fix.

**Query over-fetch.** `getProductCategories()` includes every product AND every
`ProductImage`, and the `(site)` layout calls it for the nav on every public
page. Same shape used by every `generateStaticParams`. Needs a nav-shape reader
(names/slugs only).

**`components/smoothScroll.tsx` leaks a gsap ticker.** The cleanup calls
`gsap.ticker.remove((time) => lenis.raf(time * 1000))` with a NEW closure, so
the added callback is never removed and keeps running against a destroyed Lenis.
Hoist the handler into a named const. Also: it wraps `/admin` too, which does
not want Lenis at all.

**Two DataTables.** `components/admin/data-table/DataTable.tsx` (164) serves 11
catalog tables; `components/admin/dashboard/data-table.tsx` (376) serves ONE
dashboard page with a different API. Deleting the second is ~376 lines.

**Verification numbers from this session:** `tsc --noEmit` clean;
`vitest run --project unit` PASS(549)/FAIL(0); `pnpm test` PASS(701)/FAIL(8) —
all 8 in the `auth` tier, all `PageNotFoundError: Cannot find module for page:
/api/auth/[...all]/route`, i.e. the already-documented stale `.next/dev`
condition, not a regression.

**No duplicate translation keys across modules** — checked programmatically
